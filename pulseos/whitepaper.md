# PulseOS · 脉冲式边缘计算引擎

**官方站点文案与产品白皮书**
版本 1.0 · 2026-10

## 一、品牌定位

### Slogan

> **常驻内核之上，脉冲一切应用。**

### 一句话定义

PulseOS 是一个**状态极简、按需唤醒**的边缘计算运行时。它把"进程常驻"替换为"状态驻留"——应用在两次调用之间不存在，只在需要的那几毫秒里存在。

### 三条设计公理

| 公理 | 含义 |
|---|---|
| **空闲即零成本** | 不运行时只占磁盘上一个状态箱，不占 CPU、不占内存 |
| **状态可搬运** | 状态与机器解耦，同一份状态可在任何一层硬件上恢复 |
| **内核不自造** | 不重写操作系统内核，借用宿主内核，只脉冲其上的一切 |

## 二、行业痛点

### 痛点一：常驻即浪费

一个典型 Web 站点，99% 的时间在等待请求。但为这个"等待"，你必须维持一台虚拟机、一个操作系统、一个 Web 服务器、若干运行时进程。

**你付 100% 的算力账单，买到 1% 的有效计算。**

### 痛点二：Serverless 的冷启动地狱

无服务器架构解决了空闲浪费，却引入新问题——冷启动动辄数百毫秒到数十秒。原因是状态太大：完整运行时镜像需要被反复加载、解压、初始化。

**根本矛盾：状态越大，恢复越慢。**

### 痛点三：为一个定时任务启动一台服务器

跑一个每天执行一次的脚本，需要一台机器、一个 OS、一个容器运行时、一个调度器。**为此付出的运维复杂度，远超任务本身。**

### 痛点四：密钥散落在云端

微服务架构中，API 密钥通常被注入云端镜像或配置中心。一旦镜像泄漏、日志误打、权限配错，密钥即刻外泄——而密钥一旦离开你的设备，你就再也无法证明它没有被复制。

## 三、核心能力

### 3.1 毫秒级脉冲唤醒

**实测：p50 = 4.7 ms，p95 = 7.1 ms，p99 = 8.5 ms**
（4 个服务、358 字节状态、1000 次激活统计）

一次完整脉冲包含三个阶段：

```
① 激活 activate   从状态箱恢复热状态       ~1.9 ms
② 执行 work       运行业务逻辑              ~0.004 ms
③ 挂起 suspend    状态落盘 + 释放内存       ~2.7 ms
```

**激活与挂起占 99% 的时间。这意味着：优化业务逻辑没有意义，优化状态大小才是一切。**

### 3.2 状态与数据量脱钩

这是 PulseOS 最关键的能力。

传统做法把全部数据塞进状态，导致状态随数据线性膨胀。PulseOS 采用**日志结构存储**——数据进只追加的段文件，索引存在段尾，热状态里只有**段清单 + 游标**。

实测：

| 数据量 | 冷数据（磁盘） | 热状态（进状态箱） | 比值 |
|---|---|---|---|
| 100 条 | < 1 KB | **160 B** | — |
| 5 000 条 | 21 KB | **177 B** | 121× |
| 200 000 条 | 868 KB | **196 B** | 4 428× |
| 300 000 条 | 1.27 MB | **197 B** | 6 600× |
| 1 000 000 条 | 4.24 MB | **118 B**（压缩后） | 36 947× |

**数据翻一万倍，热状态只翻 1.2 倍。** 那 1.2 倍来自段清单条目，与记录数量无关。

**这条性质决定了 PulseOS 的能力边界：它不限制数据量，只限制"活跃状态"大小。**

### 3.3 BYOK 密钥模型

**Bring Your Own Key —— 系统本身不持有任何密钥。**

```
┌──────────────────────────┐
│  用户自己的设备            │
│  .secrets/*.env          │  ← 密钥只在这里
│  vault 进程               │
│    收请求 → 调 API → 回    │
└──────────────────────────┘
           ↕ 信令通道
┌──────────────────────────┐
│  远端执行节点              │
│  只发问题，只收答案         │  ← 拿不到密钥
└──────────────────────────┘
```

**安全性的来源不是加密，是架构：密钥从未离开那台设备，因此不存在"在传输中被截获"这件事。**

这同时解决滥用问题——每个用户用自己的额度，**架构上无法借用他人算力**。

### 3.4 算力分层路由

同一份状态箱，可在不同层级恢复。调度器按**延迟预算**自动选层：

| 层 | 算力来源 | 激活延迟 | 成本 | 定位 |
|---|---|---|---|---|
| **T0** | 本机设备 | **< 10 ms** | ¥0 | 主力：日常交互 |
| **T1** | 邻居设备（P2P） | 0.3 ~ 3 s | ¥0 | 协作：算力共享 |
| **T2** | 公共 CI 资源 | **18 ~ 128 s** | ¥0 | 兜底：离线批处理 |
| **T3** | 付费云主机 | < 1 s | 按需 | 可靠：高可用兜底 |

**T0 + T1 覆盖 95% 的使用场景，且零成本。**

## 四、系统架构

PulseOS 的核心判断是：**"完整操作系统"这个词必须被拆开。**

| 层级 | 运行机制 | 说明 |
|---|---|---|
| **硬件 / 宿主内核** | 常驻 | 由物理机或云平台提供。PulseOS 不改动、不虚拟化、不模拟 |
| **init / 系统服务** | 部分常驻 | 依赖宿主进程树，负责基础网络与存储挂载 |
| **服务进程** | **脉冲** | 核心创新层。按需唤醒，执行完毕立即释放 |
| **用户会话与数据** | **状态箱** | 序列化为游标与索引，随时打包、随时恢复 |

### 明确不做的事

| 不做 | 原因 |
|---|---|
| 自研操作系统内核 | 内核状态巨大、硬件绑定、无法序列化。这是物理约束，不是工程取舍 |
| 软件模拟指令集 | 模拟器**消耗**算力而非创造算力。实测 qemu 模拟比原生慢 7.9 倍 |
| 脉冲化 init 进程 | PID 1 被挂起会导致全部子进程变孤儿并被清理 |

**PulseOS 的边界画在这里，因为越过这条线之后，一切都会失效。**

## 五、性能数据

### 5.1 脉冲延迟 vs 状态大小（决定性曲线）

| 热状态大小 | 激活 | 挂起 | 总计 | 判定 |
|---|---|---|---|---|
| 4.3 KB（100 条） | 3.4 ms | 3.6 ms | **7.1 ms** | 真脉冲 |
| 44.7 KB（1 000 条） | 3.5 ms | 7.8 ms | **11.4 ms** | 真脉冲 |
| 232 KB（5 000 条） | 10.2 ms | 21.3 ms | **31.5 ms** | 可用 |
| 955 KB（20 000 条） | 31.6 ms | 69.1 ms | **101 ms** | 勉强 |
| 2.36 MB（50 000 条） | 79.6 ms | 145 ms | **224 ms** | 勉强 |
| 14.7 MB（300 000 条） | 539 ms | 833 ms | **1 371 ms** | 已退化 |

**架构承诺：只要热状态控制在 1 MB 以内，PulseOS 保证 20 ms 以内的脉冲往返。**

### 5.2 日志结构存储的效果

状态与数据脱钩后，同一数据量下的延迟对比：

| 数据量 | 全量状态方案 | **日志结构方案** | 提升 |
|---|---|---|---|
| 1 000 条 | 11.4 ms | **7.1 ms** | 1.6× |
| 50 000 条 | 224 ms | **11.6 ms** | 19× |
| 300 000 条 | 1 371 ms | **13.4 ms** | **102×** |

### 5.3 随机访问性能

状态压缩不能以牺牲读性能为代价。20 万条数据集：

| 操作 | 耗时 |
|---|---|
| 随机读（平均） | 449 µs |
| 冷读（清缓存） | 1.31 ms |
| 尾部读取 5 条 | 1.15 ms |
| 正确性 | 500/500 全部命中 |

### 5.4 带宽调度

在强制预算下（1 MiB/小时 = 291 B/s）：

| 策略 | 每小时用量 | 占预算 |
|---|---|---|
| 朴素逐条 JSON（10 Hz） | 13.90 MB | **1 390%** ❌ |
| JSON 合并（1 Hz） | 1.48 MB | 148% ❌ |
| 二进制全量（1 Hz） | 168.8 KB | 16.5% ✅ |
| **二进制差分（1 Hz）** | **56.1 KB** | **5.5%** ✅ |

**压缩比 254×。** 其中约 46% 来自"去掉 topic 字段"——单个 topic 字符串比载荷本身还大。

公平性验证：6 个节点中 1 个试图发送 100 倍流量，实际获得份额被限制在 16.7%（1/6），**Jain 公平指数 = 1.0000**。

## 六、快速开始

### 6.1 安装运行时

```bash
git clone <repo> && cd pulse
node demo.js        # 4 个服务示例 + 1000 次延迟统计
node benchls.js     # 状态脱钩 / 延迟 / 随机读 三组验证
```

无外部依赖。Node.js 18+ 即可。

### 6.2 定义一个服务

```js
const { Proc2 } = require('./proc2');

const proc = new Proc2({
  name: 'notes',
  handlers: {
    add:  (store, _, text) => ({ state: null, result: store.append({ t: text }) }),
    list: (store, _, n)    => ({ state: null, result: store.tail(n) }),
    at:   (store, _, i)    => ({ state: null, result: store.get(i) }),
  },
}, '/var/pulse/notes');
```

### 6.3 脉冲调用

```js
let box = null;                     // 状态箱：初始为空
let r = proc.pulse(box, 'add', '第一条记录');
box = r.bytes;                      // 118 字节，随便存哪里

r = proc.pulse(box, 'list', 10);    // 从 118 字节恢复，读回数据
// r.totalMs ≈ 7 ms
```

**`box` 就是全部需要持久化的东西。** 它小到可以放进一个 MQTT 消息、一个 Git 提交、一行数据库字段。

### 6.4 部署到远端

```bash
# 用户设备：启动 vault（持有密钥）
VAULT_CHAN=<随机串> node vault.js

# 远端节点：发起调用（拿不到密钥）
VAULT_CHAN=<随机串> node agent/brain.js --status
VAULT_CHAN=<随机串> node agent/brain.js "你的问题"
```

## 七、适用与不适用

### ✅ 适用

| 场景 | 为什么合适 |
|---|---|
| AI Agent 执行环境 | 调用稀疏、每次状态小、需要极速响应 |
| 微服务网关与信令路由 | 无状态、高频、状态箱极小 |
| 物联网边缘调度 | 设备算力弱，正需要轻量运行时 |
| 定时任务 / 自动化脚本 | 天然脉冲式，空闲零成本 |
| 轻量游戏服务器信令层 | 状态可序列化，延迟要求毫秒级 |
| 多租户 BYOK 服务 | 密钥天然隔离，无需中心化托管 |

### ❌ 不适用

| 场景 | 原因 |
|---|---|
| 重型桌面 GUI 应用 | 图形上下文无法序列化 |
| TB 级本地磁盘 I/O 数据库 | 状态远超 1 MB 阈值，脉冲退化 |
| 要求 100% SLA 的核心交易系统 | 依赖宿主生命周期，无法承诺绝对可用 |
| 实时音视频流 | 需要常驻连接与流式处理 |
| 秒级以内必须响应的控制回路 | 需常驻，脉冲不适用 |

**PulseOS 不是万能引擎。它在"稀疏调用 + 小状态"这个象限里是极优解，在其他象限里不成立。**

## 八、与既有方案对比

| | 传统 VPS | Serverless | **PulseOS** |
|---|---|---|---|
| 空闲成本 | 100% | 0 | **0** |
| 冷启动 | 30 s（重启） | 100 ms ~ 数秒 | **7 ms** |
| 状态持久化 | 磁盘 | 需外部存储 | **状态箱（110 B 起）** |
| 状态可搬运 | ❌ | ⚠️ 受限 | **✅ 任意层** |
| 密钥位置 | 云端 | 云端 | **用户设备** |
| 运维复杂度 | 高 | 中 | **低（无镜像、无容器）** |

**与 Lambda / Firecracker 的关系：** 同一技术谱系的不同切口。它们是通用 Serverless 平台，PulseOS 是面向"状态极简"场景的极窄优化——**放弃通用性，换取状态箱的极致压缩。**

## 九、工程约束与已知限制

诚实列举，因为这决定了它能否被信任。

| 限制 | 影响 | 现状 |
|---|---|---|
| 无删除语义 | 只能追加，无法删除单条 | 未实现（需墓碑 + 压缩） |
| 无段合并 | 段文件持续累积 | 未实现（需 LSM compaction） |
| 单条读需解压整块 | 449 µs，不算快 | 可优化（块内偏移索引） |
| 无并发控制 | 多写者会损坏数据 | 需外部文件锁 |
| 无 CRC 校验 | 位翻转无法发现 | 未实现 |
| 依赖宿主生命周期 | 宿主重启即丢失运行时 | 设计如此 |

**当前状态：核心引擎已验证，尚不是生产级存储。** 上述六项完成前，不应承载不可恢复的数据。

## 十、开源与使用边界

**许可：** MIT

**项目定位：** 提供调度算法与状态管理引擎。不提供算力、不提供托管、不提供 SLA。

### 关于公共资源的使用

PulseOS 的分层设计允许接入公共 CI 资源（T2 层）作为离线批处理兜底。**请遵守相应平台的服务条款：**

- 公共 CI 资源的设计用途是构建与测试，单次运行有时长上限
- **不应**用于长时间占位、代理转发、挖矿或其他与项目无关的活动
- 合理用法：定时任务、构建、批处理——**与本地执行没有本质区别的工作**

**判断标准很简单：如果这件事你会在自己电脑上跑，那它在哪里跑都合理；如果你不会，那它在哪里跑都不合理。**
