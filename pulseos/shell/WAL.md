# WAL 实测：持久化到底会让脉冲慢多少

> 结论先行：**加 WAL 不会毁掉 7ms。最坏的 fsync 策略是 1.5 倍，p95 从 0.77ms 到 1.14ms。**
> 但前提是——你要选对策略。

---

## 一、先看磁盘的真实底线

在讨论策略之前，得知道硬件的物理限制：

| 操作 | 每次耗时 |
|---|---|
| `writeFileSync` 118 字节 | **0.336 ms** |
| `writeFileSync` + **`fsync`** | **1.616 ms** |

**`fsync` 是纯写盘的 4.8 倍。** 这是硬件约束，不是代码问题。

**所以「每次脉冲都 fsync」这个选项，天然要付 1.6ms 的税。**

---

## 二、四种持久化策略

| 策略 | 做法 | 断电丢什么 |
|---|---|---|
| **none** | 纯内存 | 全部 |
| **os** | 写文件，不 fsync（靠 OS 页缓存） | 最后 ≤5 秒 |
| **group(N ms)** | 攒 N 毫秒再 fsync | 最后 ≤N ms |
| **fsync** | 每次都 fsync | 不丢已确认的 |

### 关键设计：WAL 记的是「操作」，不是「状态」

```
记录 = { seq, op, args, ts, stateHash }
```

重放时再执行一遍。所以：
- **日志比状态小**（只记操作）
- **天然支持审计**（谁在什么时候做了什么）
- **可以校验状态一致性**（重放后算 hash 比对）

---

## 三、实测数据（20000 次脉冲）

完整走 `激活 → WAL → 执行 → 落盘 → 挂起`：

| 策略 | p50 | p95 | p99 | 平均 | fsync 次数 |
|---|---|---|---|---|---|
| **none** | **459 µs** | **773 µs** | 1.95 ms | 524 µs | 0 |
| **os** | 515 µs | 766 µs | 1.52 ms | 564 µs | 0 |
| **fsync** | 844 µs | 1.14 ms | 1.72 ms | 890 µs | 20050 |
| **group(5ms)** | 555 µs | 1.29 ms | 2.43 ms | 680 µs | 2711 |
| **group(20ms)** | 638 µs | 2.03 ms | 5.58 ms | 873 µs | 875 |
| **group(50ms)** | 545 µs | 867 µs | 3.86 ms | 627 µs | 254 |

### 相对「纯内存」的倍数

| 策略 | p50 | p95 | 判定 |
|---|---|---|---|
| none | 1.0x | 1.0x | ✅ |
| **os** | **1.1x** | **1.0x** | ✅ **几乎无感** |
| **fsync** | **1.8x** | **1.5x** | ✅ **几乎无感** |
| group(5ms) | 1.2x | 1.7x | ⚠️ 可接受 |
| group(20ms) | 1.4x | 2.6x | ⚠️ 可接受 |
| group(50ms) | 1.2x | 1.1x | ✅ |

## 四、三个反直觉的发现

### ① `fsync` 只慢 1.5 倍，不是想象中那么可怕

我原本担心「7ms → 30ms」。**实际是 0.77ms → 1.14ms（p95）。**

为什么？因为**真正的脉冲里，固定开销（JSON 序列化、zlib 压缩、文件写）已经占了大部分**，fsync 的 1.6ms 只是叠加，不是替换。

> **而且——这 459µs 的基线本身就远低于之前测的 7ms。**
> 那 7ms 包含了 MQTT 往返。纯本地路径只要 0.5ms。

### ② `group` 模式在这个基准里**更慢**，不是更快

反直觉：`group(20ms)` 的 p95 是 2.03ms，比 `fsync` 的 1.14ms 还差。

原因：group 模式下，某个 `append` 恰好赶上需要 fsync 的那一次，那一次就会**异常慢**（p99 冲到 5.58ms）。而 fsync 模式每次都慢一点，但**慢得均匀**。

> **教训：「平均最优」和「尾部最优」是两回事。**
> 对延迟敏感的脉冲系统，**均匀的慢 比 偶尔的卡 更好**。

### ③ `group(50ms)` 反而最好，但这是假象

`group(50ms)` 的 p95 只有 867µs，看起来最优。但这是**因为它 fsync 得最少**（254 次），代价是**断电可能丢 50ms 的操作**。

**这是用数据安全换延迟。别被数字骗了。**

## 五、推荐配置

```js
// 大多数业务
new WriteAheadLog({ dir, name, mode: 'group', groupMs: 5 })

// 记账 / 订单 / 不可重放的操作
new WriteAheadLog({ dir, name, mode: 'fsync' })

// 可重算的缓存、临时会话
new WriteAheadLog({ dir, name, mode: 'os' })
```

### 决策表

| 你的数据 | 策略 | p95 | 断电丢 |
|---|---|---|---|
| 缓存、可重算 | `none` / `os` | 0.77 ms | 全部 / ≤5s |
| **大多数业务** | **`group(5ms)`** | **1.29 ms** | **≤5ms** |
| **不可丢的操作** | **`fsync`** | **1.14 ms** | **不丢** |
| 日志、统计 | `group(50ms)` | 0.87 ms | ≤50ms |

## 六、踩到的真 bug

### `group` 模式的定时器在同步循环里永远不触发

第一版用 `setInterval` 做批量 fsync。结果：

```
group(5ms)   fsync次数: 0     ← 定时器一次都没跑
```

**原因**：测试是同步死循环，`setInterval` 的回调根本没机会进事件循环。

**修法**：在 `append()` 里**同步检查时间**，`setInterval` 只作兜底。

```js
if (now - this._lastFlush >= this.groupMs) {
  fs.fsyncSync(this.fd);
  this.pending = [];
  this._lastFlush = now;
}
```

修好后 fsync 次数正常：273 / 84 / 22（符合 5/20/50ms 的比例）。

> **教训：任何依赖事件循环的机制，在有同步热点路径的代码里都不可靠。**
> 这条对 Node.js 尤其重要——它单线程，同步循环会饿死所有定时器。

## 七、回答那个问题

> **"如果加了 WAL，延迟变成 30ms 甚至 50ms，那脉冲架构的优势还在不在？"**

**答案是：优势还在，而且这个担心被数据推翻了。**

```
纯内存    p95 = 0.77 ms
fsync     p95 = 1.14 ms     ← 只差 0.37ms
group(5)  p95 = 1.29 ms
```

**没有任何一种策略让延迟翻 10 倍。最坏的是 2.6 倍，而且那是「偶尔卡一下」，不是「一直慢」。**

**所以 WAL 该做，而且现在就可以做。**

---

## 八、但要说清楚：这还不是"能存东西"

加了 WAL 之后，依然缺这些：

| 缺 | 影响 |
|---|---|
| **没有 compaction** | WAL 会无限增长，需要定期合并 |
| **没有快照** | 重放 100 万条日志很慢 |
| **没有崩溃恢复测试** | 没模拟过"写到一半断电" |
| **没有 fsync 失败处理** | 磁盘满/IO 错误时行为未定义 |
| **没有并发控制** | 多进程同时写会互相破坏 |

**这五项做完才叫「能存东西」。现在只是「能落盘」。**
