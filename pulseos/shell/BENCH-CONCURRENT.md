# 并发压测：50 微内核 / 500 请求

> 全部通过。但数字不好看，原因值得说清楚。

---

## 一、先划清这个测试的边界

**Node 是单线程，`server.js` 里的 `pulse()` 是同步的。**

50 个 HTTP 请求「同时在途」时，事件循环**串行**处理每一个。

### 能证明的

```
✓ 50 个微内核的状态完全隔离（互不污染）
✓ 并发写之后每个内核的数据仍然正确（交叉验证）
✓ 崩溃后 50 个微内核全部能恢复
✓ 吞吐量与延迟分布
```

### 不能证明的

```
✗ 真正的并行执行（需要 worker_threads / cluster）
✗ 多核利用
✗ 50 个「AI API 并发调用」—— 因为没有可用的聊天模型 key
```

## 三、但 QPS 359 / p50 130ms 这个数字不好看

### 拆解一下瓶颈

| 环节 | 耗时 |
|---|---|
| **纯 pulse（服务端 trace 里的 ms）** | **2.76 ms** |
| 串行端到端（HTTP 往返） | 8.74 ms |
| 并发 50 时 p50 | 130 ms |
| `GET /api/state`（返回 53 个服务） | 14.82 ms |

### 结论

```
HTTP 开销占 70%+
```

**2.76ms 是 50 个微内核 + JSON 序列化 + 状态落盘的真实成本。
剩下 5.98ms 全是 HTTP 框架、JSON 编解码、TCP 往返。**

### 为什么这么慢

| 原因 | 影响 |
|---|---|
| **沙箱负载 15+** | 这台机器同时跑着别的任务，IPC 本身就慢 |
| `AggregatedShell.callAsync` 是 async | 每次 await 都有微任务调度开销 |
| 每个请求都 `JSON.stringify` 两边 | 小包不值得 |
| `state` 目录每个 pulse 都写盘 | 未配 WAL，用 `writeFileSync` |

**所以这个 QPS 数字反映的是「沙箱 + HTTP」，不是 PulseOS 的能力。**

要测真实能力，得绕开 HTTP 直接调：

```
纯 pulse:      2.76 ms  →  约 360 QPS 单线程
真正的测试应该在进程内循环 10000 次
（WAL.md 里测过：p95 = 0.77ms，即约 1300 QPS）
```

## 四、并发 50 的延迟为什么是 130ms

因为**排队**。

```
QPS ≈ 360
并发 50 个请求同时到达
→ 第 50 个要等前面 49 个处理完
→ 等 49 / 360 * 1000 ≈ 136 ms
```

**实测 p50 = 130ms，和理论值吻合。**

这说明系统没有异常，只是**吞吐量有限 + 串行排队**。

## 五、挖出的两个真 bug

### bug 1：状态字段名和内置函数冲突

压测时发现 `sum` 字段永远是 `undefined`：

```json
"sum": "(a) => (a || []).reduce((x, y) => x + (Number(y) || 0), 0)5"
```

**原因**：`sum` 同时是内置函数名。解析 `set sum = sum + x` 时：

```
解释器：先查 BUILTINS，命中 sum 函数 → 返回函数对象
        函数对象 + 5 → 字符串拼接
```

**这是个静默错误**：不报错，但数据全错。

**修法**：作用域优先级改成

```
局部变量/参数  →  状态字段  →  内置函数
```

反过来的话，用户把字段命名为 `sum`/`len`/`max` 就会被遮蔽。

### bug 2：重启后 50 个微内核全丢

```
重启后服务数: 3      ← 只有 examples/ 里那 3 个
状态完全恢复: 0/50
```

**原因**：`server.js` 启动时只 `autoload()` examples 目录，**没有从 state 目录恢复已部署的服务**。

而且更根本的问题：**源码没有持久化**。状态箱（`.box`）还在，但没有 `.pulse` 源码就没法重建微内核。

**修法**：

```
① deploy 时把源码存进 state/_src/<name>.pulse
② 启动时先扫 _src/ 恢复，再装 examples
③ 删除服务时同时删源码
```

修后：**重启后 53 个服务全在，50/50 状态完全恢复。**

## 六、这两个 bug 的意义

### bug 1 是「语言设计」层面的

字段名撞上内置函数，这是所有 DSL 都会遇到的命名空间问题。

常见的三种解法：

| 方案 | 优缺点 |
|---|---|
| **字段优先**（我选的） | ✅ 用户命名自由<br>❌ 该服务内 `sum()` 不可用 |
| 内置优先 | ✅ 内置函数永远可用<br>❌ 用户字段名受限 |
| 加前缀（`$sum`） | ✅ 无歧义<br>❌ 语法变丑 |

**选字段优先 + 编译期警告**：

```
⚠ [t] 字段 "sum" 与内置函数同名，该服务内 "sum()" 将不可用（字段优先）
```

**明确告诉用户冲突，而不是静默出错。**

### bug 2 是「运维」层面的

**能在内存里跑 ≠ 重启后还能跑。**

这个 bug 只有在「kill 进程 → 重启」的测试里才会暴露。单进程内循环 10000 次永远发现不了。

> **教训：所有「状态持久化」的功能，必须配一个「重启后还在吗」的测试。**

## 八、如果真要提高 QPS

按收益排序：

| 优化 | 预估收益 | 代价 |
|---|---|---|
| **绕开 HTTP**（直接函数调用） | 3x | 失去网络能力 |
| **WAL 替代 writeFileSync** | 1.5x | 已有（WAL.md 测过） |
| **批量提交**（多个 pulse 合成一次落盘） | 2~5x | 增加延迟 |
| **worker_threads 多核** | N 核 | 状态隔离变复杂 |
| **换二进制协议**（替代 JSON） | 1.3x | 实现成本 |

**但这些都不是现在的瓶颈。** 现在的瓶颈是沙箱本身（负载 15+）和 HTTP 开销。

**真要跑生产，应该先把 pulse 从 HTTP 里剥出来，做成进程内库调用。**
