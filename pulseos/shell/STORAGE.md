# Compaction 与崩溃恢复：从「能落盘」到「能存东西」

> 两件苦力活都做完了。
> 过程中挖出 **两个会静默丢数据的 bug**，和 **一个测试本身的盲区**。

---

## 一、先看问题有多大

### WAL 会无限增长

| 记录数 | WAL 大小 |
|---|---|
| 4 000 | 333 KB |
| 20 000 | 1.67 MB |
| **1 000 000** | **82 MB** |

单条记录 86 字节（JSON + zlib level 1 + 12 字节头）。

### 重放会很慢

```
10 万条:  105 ms
100 万条: 约 1.0 秒    ← 而这期间服务完全不可用
```

**所以 compaction 不是优化，是必需品。**

---

## 二、挖出的第一个 bug：轮转丢数据（v1）

```
写入 100000 条
replay 只拿到 38568 条
第一条 args=[61432]     ← 前 61432 条消失了
```

**原因**：v1 只有单个 `.wal` 文件，写满后 `rename` 成备份，然后新建。

但 `replay()` 只读当前文件——**旧的全部看不见了。**

目录里的证据：
```
t.wal                 2592 KB    ← 当前段，38568 条
t.wal.1792987154160   4096 KB    ← 旧的，被无视
```

**修法**：改成多段（`wal-<startSeq>.log`），`replay()` 扫全部段合并。

```
修后：写入 100000 条，replay 拿到 100000 条  ✓
      段数 26，第一条 args=[0]，最后 args=[99999]
```

## 三、挖出的第二个 bug：compaction 删段导致文件名覆盖

改成分段后，测 compaction 又发现：

```
写 50000 条，compaction 三次
恢复后 n = 47341  (期望 50000)     ← 丢了 2659 条
```

**原因**：段名用了 `segs.length + 1`。

```js
const idx = this.segs.length + 1;   // ← compaction 删段后长度回退
```

删掉 4 个段后 `segs.length` 变小，新段的序号**和已存在的旧段重复**，直接覆盖。

**修法**：用 `startSeq`（单调递增）做段名，永不重复。

```js
const file = 'wal-' + String(afterSeq + 1).padStart(12, '0') + '.log';
```

修后：

```
恢复后 n = 50000  (期望 50000)  ✓ 完全一致
重放记录 = 5000 条（正好 50000 - 45000）
```

> **教训：任何用「数组长度」做标识的地方，在有删除操作的场景里都是定时炸弹。**

## 四、Compaction 的三条正确性规则

这不是「把旧日志删掉」那么简单。删错了就永久丢数据。

```
① 快照原子        写 tmp → fsync → rename → fsync(dir)
② 重放幂等        跳过 seq <= snapshotSeq 的记录
③ 删段在快照后    只有快照 fsync 落盘之后才删旧段
```

### 规则②为什么是关键

考虑这个崩溃场景：

```
1. 写完快照 → 快照已落盘
2. 【崩溃】← 旧段还没删
3. 重启 → 快照 + 旧段都在
```

如果重放时**不跳过** `seq <= snapSeq`，那些操作会被应用两遍，**状态翻倍**。

有了规则②，这个中间状态天然安全——**不需要两阶段提交**。

### 规则①的细节：为什么还要 fsync 目录

```js
fs.renameSync(tmp, dst);     // 原子替换
fsyncSync(dirFd);            // ← 这一步容易忘
```

`rename` 在文件系统里改的是**目录项**。如果只 fsync 了文件内容，没 fsync 目录，断电后可能「文件内容在，但目录里查不到这个名字」。

## 五、Compaction 实测效果

```
写 50000 条，每 15000 条 compaction 一次（共 3 次）

  compaction @ seq=15000  快照 <1KB  删段 3   12ms
  compaction @ seq=30000  快照 <1KB  删段 4   10ms
  compaction @ seq=45000  快照 <1KB  删段 4   14ms
```

| | 有 compaction | 无 compaction | 提升 |
|---|---|---|---|
| 磁盘 | **408 KB** | 3 225 KB | **7.9x** |
| 恢复耗时 | **295 ms** | 1 363 ms | **4.6x** |
| 重放条数 | **5 000** | 50 000 | **10x** |

**恢复后 `n = 50000`，完全一致。**

## 六、崩溃恢复测试：40 轮 SIGKILL 全部通过

### 测试做法

```
1. 子进程不断写 WAL，每次成功后打印「已确认的 n」
2. 父进程等到写入条数达到随机目标（30~800），再等 0~15ms 抖动
3. SIGKILL（不是 SIGTERM —— 不给任何清理机会）
4. 重新打开，恢复，校验三件事
```

### 三条校验

| 校验 | 内容 | 不过意味着 |
|---|---|---|
| ① **不丢已确认** | `recovered.n >= 最后一次 ack 的 n` | 致命 bug |
| ② **无跳号** | WAL 里 seq 必须连续 | WAL 断裂 |
| ③ **状态自洽** | 恢复出的 `sum` 必须等于 `1+2+...+n` | 状态被破坏 |

### 结果

| 配置 | 通过 | 最大丢失 |
|---|---|---|
| os（不 fsync） | 10/10 | 0 |
| fsync（每次刷） | 10/10 | 0 |
| fsync + compaction | 10/10 | 0 |
| group(5ms) | 10/10 | 0 |

**40 轮全部通过，零丢失，无跳号，状态自洽。**

有时恢复出的 `n` 比 ack 多 1（`acked 425 → recovered 426`）——这是**正确的**：
子进程写完 WAL 但还没来得及打印 ack 就被杀了。

## 七、⚠️ 必须说清：这个测试有个盲区

`os` 模式（完全不 fsync）在测试里也是 **0 丢失**。

**这不能说明 `os` 模式安全，只说明测试测的是「进程崩溃」不是「断电」。**

| 模式 | 写入 2000 条 | 断电会丢 |
|---|---|---|
| none | fsync 0 次 | **全部** |
| os | fsync 0 次 | **最多 2000 条** |
| group(5ms) | fsync 28 次 | 最多 1972 条 |
| **fsync** | **fsync 2000 次** | **0 条** |

### 为什么

```
kill -9 杀死进程 → 数据还在 OS 页缓存里 → 另一个进程能读到 → 不丢
真·断电        → 页缓存蒸发 → 只有 fsync 过的才在磁盘上 → 会丢
```

**页缓存是操作系统级的，不是进程级的。** 所以进程崩溃测试永远测不出 fsync 缺失。

### 那怎么办

真正的「断电测试」在用户态做不到，只能：

1. **靠 fsync 次数的正确性**（上面那张表）
2. **靠文件系统语义保证**（ext4 的 data=ordered 模式）
3. **真机测试**：跑在树莓派上拔电源

**所以我的结论是：**

> **这个测试证明了「进程崩溃安全」，没有证明「断电安全」。**
> **`fsync` 模式的断电安全来自「每次写完都 fsync」这个纪律，不是来自测试结果。**

## 八、目录结构与恢复流程

```
dir/
  snap-000000030000.snap     快照（原子写，可校验 CRC）
  snap-000000045000.snap
  wal-000000043740.log       段，文件名 = 起始 seq
  wal-000000047670.log
  .snap-xxx.tmp              ← 崩溃残留，开机自动清理
```

### 恢复流程

```
1. 清理 .tmp 残留
2. 从新到旧找最新【能通过 CRC 校验】的快照
3. 扫描所有段，读出 seq > snapSeq 的记录
4. 按 seq 排序，逐条 apply
```

**任何一步损坏都不致命**：快照 CRC 失败就试更早的，WAL 记录 CRC 失败就当作尾部截断。

```

```

**前两项是必须补的，第三项看状态规模。**
