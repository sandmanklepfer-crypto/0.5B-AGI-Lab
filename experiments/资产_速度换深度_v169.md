```

```
| 问题空间 | 要试多少次 | 10^5 够吗 |
|---|---|---|
| 2^16 | 3×10⁴ | ✅ 勉强 |
| 2^20 | 5×10⁵ | ❌ |
| 2^30 | 5×10⁸ | ❌ |

**★ 但「速度 + 验证器」可以**: 验证器剪枝把指数从 n 压到 0.6n
(SAT n=100: 2^100 → 2^60, 省 1.1×10¹²)

## 五、★ 零件的正确组合 (按重要性)

```
① ★★★ 验证器 —— 唯一的「方向来源」
     L0 无        → 不可能
     L1 二元       → 只能盲搜 C(d,3)
     L2 部分反馈    → C(d,3) 降到 O(d)   ← 最大杠杆

② ★★  混沌/小网络 —— 只负责「快」, 不负责「对」
     配 L1 → 原地打转 (期望不变)
     配 L2 → 强强联合 (27 次 vs 46 次)

③ ★   错题本 —— 让系统「越用越快」(100次重复 → 77113×)

④     锚点 + 倒查 —— 长链永不累积误差 + 出错能二分定位
```

**一句话**:
> **混沌给「可能」, 验证器给「方向」, 错题本给「积累」, 锚点给「可靠」。**
> **四者缺一, 速度都换不来正确性。**

## 六、锚点成本账 (worth.py / backtrace2.py)

```
净收益 = L0·(1-p)^L0 / c      (L0=锚点间隔, p=单步误差, c=验证/推理成本)

实测: c = 0.30 (验证一次 = 推理一步的 1/3)
      p = 0.35 (当前粗糙码本)  → 只值 3×

若把识别层做好:
      p = 0.01 → 净收益 127×     (每 100 步一个锚点)
      p = 0.005 → 净收益 254×
```
**★ 投入方向: 把识别层做精 (降 p), 而不是把链子拉更长。**

倒查/错题本 (backtrace2.py):
```
200 步链, 第 137 步出错
  一步步倒查 → 65 次验证
  ★ 二分倒查 → 8 次 (log 增长, 2万步也才 15 次)
100 个任务, 老出错位置只有 5 处:
  无错题本 800 次 → 有错题本 40 次 (省 20 倍)
```

## 七、总账: 推荐架构

```
感知 (连续)
  ↓ ① 识别层  (一次性付清, 允许有损 p≈0.01, 只要认出符号身份)
离散符号
  ↓ ② 混沌/小网络生成候选  (只管快, 一次给一大批)
候选集
  ↓ ③ 验证器 (L1执行 / L2部分反馈 / L3检索)  ★方向来源
  ↓ ④ 剪枝搜索 (beam / 二分)
  ↓ ⑤ 锚点 (每 L0 步确认一次) + 二分倒查
  ↓ ⑥ 错题本 (缓存否定/确认结果)
输出 (100% 可验证)
```

**适用边界 (诚实)**:
| 任务类型 | 能否用 |
|---|---|
| 形式化封闭 (算术/逻辑/代码/结构变换) | ✅ 又准又快 |
| 搜索空间 ≤10^5 | ✅ 速度即可取胜 |
| 开放生成 (写文章/聊天) | ❌ 本方案做不了 |
| 无对错可验的领域 | ❌ 验证器不存在, 整个链条失效 |

## 九、★ 九轮总结一句话
> **速度必然暴涨 (3万~86万倍), 但速度只能买「更快地迷路」。**
